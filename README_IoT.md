# NTUST RRC 器材資源管理系統 - 自動化硬體節點與 AI 協同架構書

## 專案目標 (Project Objectives)
本系統旨在實現社團器材與資源的「全自動化、使用者自主化」借還流程，透過物聯網 (IoT) 硬體節點與雲端多模態 AI 的協同合作，達成以下核心目標：
1. **無人化自主管理：** 使用者憑系統生成的 QR Code 憑證即可自主定位、領取與歸還器材。
2. **零阻力尋物體驗：** 結合語音辨識、語音播報與 LED 視覺化指引，解決特定零件或工具難以尋找的痛點。
3. **高準確度邊緣感測：** 透過邊緣運算紀錄器材狀態，大幅降低雲端 API 請求頻率，實現低延遲與低成本的庫存同步。
4. **直覺的人機介面：** 透過 OLED 螢幕與實體按鈕提供明確的操作指引與申請明細確認。

---

## 網路通訊架構與機制 (Networking & Communication)

本系統採用 **Client-Server 網域主動請求架構**，硬體端不需架設伺服器或配置固定 IP 位址，完美適應社團內網限制或開發階段的網路環境：
1. **連線路由 (MVP 階段)：** 所有硬體節點統一連線至手機行動熱點（或具備對外路由能力之區域網路），藉由蜂巢網路直連網際網路。
2. **通訊協定：** ESP32 節點始終作為 Client 端，主動向遠端 Vercel 閘道器 (`https://...vercel.app`) 發送 HTTPS POST 請求。
3. **一問一答機制 (Request-Response)：** 系統不依賴 Server Push。ESP32 發送 HTTP 請求後保持連線，Vercel 於後端處理完畢後，直接沿著同一條連線，將控制指令或查詢清單封裝於 HTTP Response 中回傳給 ESP32。

## 系統架構與 ESP32 節點任務分配 (System Architecture & Node Tasks)

系統分為三個高度解耦的實體 ESP32 節點，各自負責「語音互動」、「實體庫存感測」與「視覺授權認證」，統一透過 HTTPS 與 Vercel API 及 Google Sheets 進行資料交換。

### 節點一：語音尋物與多媒體互動站 (ESP32 #1)
* **核心功能：** 集中處理所有環境音訊輸入/輸出與空間視覺指引。
* **硬體配置：** ESP32 模組 + INMP441 (I2S 麥克風) + MAX98357A (I2S 音訊放大器) + 小喇叭 + WS2812B 尋址燈條 (x3)。
* **訊息傳遞格式：**
    * **Request:** 擷取語音特徵或字串後上傳至 Vercel API。
    * **Response:** 接收 Vercel 回傳之 JSON 格式控制指令，例如：`{"action": "light_up", "strip_ids": ["Strip_1"], "audio_url": "https://..."}`。
* **執行任務：**
    1.  **音訊採集與發送：** 監聽環境指令，錄製音訊並發送 HTTP Request 上傳雲端進行 AI 語意解析。
    2.  **查詢與定位回報：** 透過 API 查詢器材對應的實體位置與燈號。
    3.  **語音與燈光回饋：** 解析 HTTP Response 中的指令，透過 I2S 串流播放雲端生成的語音提示（如：「A是在 單晶片 類別，箱子在亮燈區域」），並同步點亮對應區域的燈條指引使用者。

### 節點二：邊緣庫存狀態感測站 (ESP32 #2)
* **核心功能：** 精準且低延遲地偵測器材箱的實體在位狀態。採「一層一機」模組化設計。
* **硬體配置：** ESP32 模組 + RC522 (RFID/NFC 讀卡機 x3，共用 SPI 匯流排，透過獨立 CS 腳位輪詢)。
* **訊息傳遞格式：**
    * **Request:** 僅在狀態變動時，發送包含裝置識別碼與該層位置快照的 JSON，例如：`{"device_id": "ESP32_C1_L1", "slots": {"A": "BOX-001", "B": "EMPTY", "C": "BOX-002"}}`。
* **執行任務：**
    1.  **邊緣狀態管理 (Edge State Diff)：** 高頻率輪詢 3 個讀卡機的 UID 狀態，並與本地快取狀態陣列進行比對。
    2.  **事件驅動更新：** 僅在偵測到器材箱位置發生「實體變動（取出或放回）」且通過硬體/軟體防抖驗證後，才主動發送 Request (Push) 至系統更新資料庫，極小化 API 呼叫次數。

### 節點三：身分授權與視覺終端 (ESP32-S3 WROOM)
* **核心功能：** 驗證借用者憑證、防護系統安全，並提供清晰的借用資訊確認。
* **硬體配置：** ESP32-S3 WROOM + OV2640 (鏡頭模組) + I2C OLED 顯示器 + 實體控制按鈕。
* **訊息傳遞格式：**
    * **Request:** 掃描成功後，發送包含借用憑證的 JSON，例如：`{"reqId": "REQ-YYYYMMDD-XXX"}`。
    * **Response:** 接收 Vercel 回傳的 JSON 陣列（包含申請人姓名、器材名稱清單等），供本地端 ArduinoJson 解析。
* **執行任務：**
    1.  **待機與喚醒：** OLED 螢幕常態顯示待機畫面與操作提示。
    2.  **手動觸發掃描：** 使用者按下按鈕後，啟動 OV2640 鏡頭準備掃描 QR Code 憑證。
    3.  **雲端資料請求：** 掃描成功後，將申請單號發送至資料庫讀取詳細清單。
    4.  **視覺明細確認：** 解析 HTTP Response 獲取的清單資料，於 OLED 螢幕上渲染借用明細，例如顯示：「申請人: XXX \n編號: REQ-... \n器材: (001) 游標卡尺」。
    5.  **領取確認：** 配合後端邏輯，完成最終的借用狀態註記與發送 Email 通知。

## 資料庫架構與工作表設計 (Database Schema & Sheets Design)

本系統後端架構於 Google 試算表上，透過以下兩張核心工作表建立「實體器材箱」與「物理櫃位硬體引腳」的資料關聯：

### 1. 箱子總表 (BoxList)
本表負責管理物理上存在的實體箱子狀態，當 Vercel 接收到邊緣端上傳的位置快照後，會在此表更新各箱子的當前位置與在位狀態。

| 箱子編號 | 大小 | 類別 | 位置 | 狀態 |
| :--- | :--- | :--- | :--- | :--- |
| BOX-001 | Large | 馬達, 齒輪 | C1-L1-A | 在櫃 |
| BOX-002 | Small | 單晶片 | C1-L1-C | 在櫃 |
| BOX-003 | Small | 傳感器 | 未偵測 | 使用中 |

* 欄位說明：
    * 箱子編號：實體箱子唯一代碼，此代碼由 ESP32 內部的 RFID UID 對照表直接轉換輸出。
    * 大小：箱子尺寸規格（Large 代表大箱子，會遮擋並佔用連續兩格物理位置；Small 代表小箱子，佔用一格位置）。
    * 類別：該箱子所內含的器材種類，支援以半形逗號分隔多個種類，供 Vercel 端的 AI 模型進行模糊語意匹配。
    * 位置：當前被感測器偵測到的實體櫃位編號。
    * 狀態：該箱子的庫存動態狀態（在庫、使用中）。

### 2. 實體櫃位映射表 (CabinetLayout)
本表作為硬體與空間的設定檔。將櫃子的三維物理空間代碼映射到特定控制晶片與實體控制引腳，確保未來系統擴充至其他櫃位層架時，無須修改硬體核心程式碼。

| 櫃位編號 | 裝置編號 | 位置 | LED腳位 | 描述 |
| :--- | :--- | :--- | :--- | :--- |
| C1-L1-A | ESP32_C1_L1 | A | Pin_12 | 第一櫃第一層底層 |
| C1-L1-B | ESP32_C1_L1 | B | Pin_13 | 第一櫃第一層中層 |
| C1-L1-C | ESP32_C1_L1 | C | Pin_14 | 第一櫃第一層頂層 |

* 欄位說明：
    * 櫃位編號：物理櫃位代碼，格式採用 Column-Layer-Position（行-層-層內位置）。
    * 裝置編號：負責感測與控制該物理區域的實體 ESP32 晶片識別碼。
    * 位置：單一層架內部的垂直堆疊位置(slot)（由下至上分別定義為 A、B、C 區）。若下層放置 Large 箱子，系統邏輯會自動將上方的 Position 預期狀態設為被佔用。
    * LED腳位：ESP32 晶片上用來獨立控制該位置燈條的 GPIO 引腳編號。
    * 描述：該物理櫃位的直觀文字描述，用於雲端 TTS 模型轉換成即時語音導引語句。

## 資料流與安全機制 (Data Flow & Security)

1.  **Client-Side (硬體端)：** 所有 ESP32 節點僅負責 I/O 採集、基本硬體驅動與 HTTP 請求發送，不直接接觸 Google Apps Script。
2.  **API Gateway (Vercel 中介層)：** 負責接收硬體請求、處理硬體驗證 (API Key/Token)、跨域防護、邏輯運算與資料格式化，並擔任多個 AI 模型的排程中心，最後將結果回傳給硬體。
3.  **Database & Notification (GAS)：** 作為封閉的內部服務，僅接收來自 Vercel 的請求，專注處理 Google Sheets 讀寫與 Email 派發。
